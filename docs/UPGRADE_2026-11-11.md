## Root cause and YouTube recovery

`app.js` had independent hard-coded **10,500 ms** limits for downloading the YouTube IFrame API and waiting for player readiness. Duration metadata had a separate **20,000 ms** deadline. The 60-second fetch timeout did not affect any of these timers. The short timers could reject a supported video before any request reached Gemini. Failed player objects could remain present, causing Retry to reuse an unready player. The loader also retained failed script elements/callback state.

The new loader shares one active API request, removes failed scripts, resets failed promises and ignores obsolete player callbacks. API load, player readiness and metadata now each have a separate 60-second default. A waiting notice appears after 10 seconds, satisfying PDF requirement 6.6 without declaring an operation failed prematurely. Real YouTube errors distinguish invalid links, unavailable/private videos, embedding restrictions, browser playback and client identification failures. No restrictions are bypassed.

Optional Render environment variables (no change required): `VIDEOQUIZ_YOUTUBE_API_TIMEOUT_MS`, `VIDEOQUIZ_YOUTUBE_PLAYER_TIMEOUT_MS`, `VIDEOQUIZ_YOUTUBE_METADATA_TIMEOUT_MS`. Public settings are clamped to 10,000–120,000 ms and expose no secrets. Normal API/auth requests allow 60 seconds for a cold service. Gemini connection timeout is 20 seconds, generation requests remain 180 seconds and overall jobs retain their 12-minute deadline. These phases are distinct; a timeout does not prove the video or Gemini caused the failure. Network loss retains the input, and duplicate active analysis requests reconnect to the saved job.

## UI and bilingual behavior

New responsive purple/neutral visual design, dashboard, recent activity, drag/drop upload, separate analysis stages, sticky video beside questions, clearer answer feedback, mobile layout and light/dark themes. No third-party UI framework, remote fonts, paid service or extra production dependency was added. Reduced-motion preferences and keyboard focus are respected. The YouTube viewport remains at least 200px high on phones.

`i18n.js` contains the English-key/Arabic catalog and dynamic-message templates. It translates UI text and accessible labels, sets `html.lang` and RTL/LTR, and saves language/theme locally. Switching does not refetch analysis, seek the player, submit answers or replace selections. Content marked `data-verbatim` (video titles, questions, options, source evidence and explanations) stays in its saved language. Browser-owned file-picker dialogs are outside the app; the visible upload control is localized.

New analyses may select Arabic or English questions. `quizLanguage` is an additive JSON field; missing values display as English for old records. A failed analysis keeps its selected language, and existing READY quizzes cannot be regenerated through the retry endpoint. Gemini is still asked to inspect actual video/audio and produce evidence-grounded questions. Routine tests supply explicit fixtures; no fake output path was added to production.

## Results and persistence

The existing `Attempt` records, immutable first answers, server scoring, Store/CloudStore and private media storage are reused. Summaries add incorrect counts, percentages and completion status without changing database tables. The dashboard averages **completed quiz percentages**, while answer totals include completed and unfinished attempts. Attempts are newest first, paginated in the UI, with up to eight completed scores in an accessible progress-bar chart.

Detailed review shows every question and all four choices. Submitted questions show selected/correct answers, explanation and evidence. Unanswered questions explicitly remain locked: their correct answers/explanations are absent from the API response. New attempts reuse the existing generated quiz without Gemini. User ownership checks are unchanged and regression-tested. Interface language is a local preference; quiz language and answers persist with server records.

## Update the existing deployment safely

1. Review this branch or the supplied Git bundle/ZIP. Do not overwrite the original NetBeans project or upload a working folder containing data/secrets.
2. Push **the development branch**, not main. Open a pull request targeting main. The verification workflow tests Java 17/21, PostgreSQL fixtures, JS/browser fixtures and the Docker build without cloud credentials.
3. Wait for all checks to pass. If no GitHub workflow runs, do not treat that as success; check Actions permissions. The connector currently rejects branch creation with HTTP 403, so a repository owner may need to push through GitHub Desktop or grant repository write access.
4. Test in a separate local folder using the existing setup/start scripts. Keep the live Render service pointed at main. No new Render or Supabase project is necessary.
5. After review and passing checks, merge the PR. The existing Render autodeploy can deploy main. Keep all current secret variables and Free plan settings. The new timeout variables are optional.
6. On the live URL verify login, a small MP4, two supported YouTube videos, retry, both languages, Next, results and existing history. Use existing saved quizzes to test review without consuming Gemini quota. Do not claim live acceptance until performed.
7. If needed, roll back the Render deployment or revert the merge commit. Do not delete the database/bucket. The additive quizLanguage field is ignored by old code, so it does not require a reverse migration.
